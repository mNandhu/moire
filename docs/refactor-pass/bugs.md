# Known bugs found by the refactor pass

Bugs surfaced while reviewing for refactors. Fixed ones are struck through with the commit.

- ~~Rescan of a missing or unmounted library folder deletes every image and its curation~~ (fixed 5c1bf8d)
- **Library scan_error is never shown in the UI.** No frontend file reads `scan_error`, so a failed scan (`Library folder not found`) or a scan that kept images (`Kept N images: library folder is empty`, `Some folders could not be read`) is invisible on the Libraries page. Found while fixing 5c1bf8d. Evidence: `grep -rn scan_error packages/frontend/src` is empty; written by `services/scanner.py` `_run`.
- **Cancelled requests render as 'done' frames in the queue card** (S8-genengine, confidence low). _frames maps failed/lost to 'failed', running to 'making', _OPEN to 'waiting', and everything else (including 'cancelled') falls through to 'done' frames with thumb None. Cancelling one request of an active batch (POST .../requests/{id}/cancel) therefore shows n finished-looking empty frames, and active_summary counts it in `finished` without a distinct state. Low confidence it is unintended, since no test or comment covers a cancelled frame. Fix: Add a `cancelled` branch in _frames returning {'state': 'cancelled', 'thumb': None} (or drop cancelled requests from frames) and have the queue card style it; add a test of active_summary after a single-request cancel. Evidence: `packages/backend/src/moire/services/generation_batches.py:405-422`, `packages/backend/src/moire/services/generation_batches.py:343-402`
- **Global keydown ignores modifier keys: Ctrl/Cmd+1..5, Alt+Arrow hijacked** (S2-imageview, confidence med). onKey tests e.key only. Ctrl+1..5 (browser tab switch), Cmd+0 (reset zoom) score the image and call preventDefault; Alt+ArrowLeft/Right (browser back/forward) and Ctrl+ArrowLeft are swallowed as prev/next; Ctrl+X / Cmd+X (cut) quarantines the image while a non-input element is focused. Escape also closes the view even while a Picker or dialog is open if the focus is not in a form field (the rating Picker popup, ConfirmDialog from Re-tag). Fix: At the top of onKey add `if (e.ctrlKey || e.metaKey || e.altKey) return;` and skip when e.defaultPrevented (so an open Picker/dialog that handled Escape wins). Put the guard in a shared helper in lib/dom.ts (`isPlainKey(e)`) since AllImagesPage's triage handler has the same shape (shortcuts.ts lists the same keys). Evidence: `packages/frontend/src/pages/ImageView.tsx:578-621`, `packages/frontend/src/lib/shortcuts.ts:44-45`, `packages/frontend/src/lib/shortcuts.ts:63-64`
- **One malformed graph aborts a whole reprojection: extract is not total and the loop has no per-row guard** (S7-prompts, confidence med). `_find_sampler` does `inp = node.get('inputs', {})` then `'positive' in inp`; a node with `"inputs": null` (or a list) raises TypeError, and `parse_comfyui` calls `.get` on it unguarded (AttributeError). Other helpers (`_resolve_text`, `comfy_loras`) do check `isinstance(inp, dict)`, so the module's own convention is 'never raise on hostile graphs' (resolve_path says 'Never raises'). In `_reproject_where` there is no try/except around `gen_metadata.extract`, so the exception propagates out of the run; `_tracked` only logs it. Every image after the bad row stays underived until the next restart/rescan, which then hits the same row first. Also `_empty` shallow-copies `_EMPTY`, so `loras`, `embeddings`, `guessed`, `guess_paths` are shared mutable objects across calls (currently safe only because each caller reassigns before mutating). Fix: In `_find_sampler`/`parse_comfyui` use `inp = node.get('inputs'); if not isinstance(inp, dict): continue`. In `_reproject_where` wrap the extract+aliases step in try/except Exception, log with the image id, and `continue` (counting it as advanced). Make `_empty` build fresh lists/dicts (`copy.deepcopy(_EMPTY)`). Add a test_gen_metadata case with `{'3': {'class_type': 'KSampler', 'inputs': None}}` and a reproject test with one poisoned raw. Evidence: `packages/backend/src/moire/services/gen_metadata.py:723-733`, `packages/backend/src/moire/services/gen_metadata.py:746-750`, `packages/backend/src/moire/services/reproject.py:186-211`, `packages/backend/src/moire/services/reproject.py:267-273`
- **Retag of an image a running AI job already passed wipes its AI tags and reports success** (L1-jobs, confidence high). `_in_flight` holds every id of a job until the whole job ends (ai_jobs.py:311-313), not until that image is tagged. `/tag` with `retag` first runs `image_tags.clear_ai` on each id, then calls `enqueue(force=req.force)`. The frontend never sends `force` (lib/ai.ts:270-275). Scenario: a 200-image 'tag untagged' job is at image 150, and the user re-tags image 5, which that job already tagged. clear_ai wipes its AI tags and rating, enqueue counts the id as skipped, and the 0-total job is marked done at once. useAiTagging then toasts 'AI tagging completed', and the image is left with no AI tags. `_in_flight` is also a set, not a refcount. A forced job overlapping another job loses its claim when the first job ends, and cancelling a queued job (ai_jobs.py:226-228) releases ids that another job still holds. Fix: Two fixes, each small. (1) In `_worker_loop`, discard each id from `_in_flight` right after its `_tag_one` (or its failure), so 'in flight' means 'not yet processed'. Leave only the unprocessed tail to the `finally`. (2) In `api/ai.py` `ai_tag`, pass `force=True` whenever `req.retag` is set, because a retag has already destroyed state and must run. Optionally make `_in_flight` a `collections.Counter` so overlapping forced jobs release correctly. Evidence: `packages/backend/src/moire/api/ai.py:149-156`, `packages/backend/src/moire/services/ai_jobs.py:160-195`, `packages/backend/src/moire/services/ai_jobs.py:306-313`, `packages/backend/src/moire/services/ai_jobs.py:220-229`, `packages/frontend/src/lib/ai.ts:270-275`, `packages/frontend/src/hooks/useAiTagging.ts:76-78`
- **Async routes block the event loop on scan/watch thread joins** (L1-jobs, confidence high). `remove_library` is `async def` and calls `cancel_scan` (a `th.join` of up to 0.5 s) and `stop_watch` (a join of up to 1 s) directly on the loop. `create_library` and `update_library` call `start_watch`, which joins the old watch thread while holding `_lock` (library_watch.py:381-384). A scan thread rarely exits within 0.5 s, because run_pool leaves running futures to finish. So deleting a big library mid-scan stalls every request, including thumbnails and the activity poll, for up to 1.5 s. main.py:83-84 deliberately runs `stop_all` off the loop for exactly this reason, so the routes are inconsistent with it. Fix: In api/libraries.py, wrap these calls in `await anyio.to_thread.run_sync(...)`: `cancel_scan`, `stop_watch`, and `start_watch` (only when replacing an existing watch). The alternative is to give `cancel_scan` and `stop_watch` a signal-only mode (`wait=False`) for async callers. Prefer the to_thread form for delete: it can then wait for the scan thread to actually end (longer join), which also closes the late-batch race noted in the hints. Evidence: `packages/backend/src/moire/api/libraries.py:131-138`, `packages/backend/src/moire/api/libraries.py:126-128`, `packages/backend/src/moire/api/libraries.py:268-276`, `packages/backend/src/moire/services/scanner.py:810-826`, `packages/backend/src/moire/services/library_watch.py:371-395`, `packages/backend/src/moire/services/library_watch.py:405-417`, `packages/backend/src/moire/main.py:83-84`
